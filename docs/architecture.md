# 陷空山 V2 架构

## 1. 目的

本文档定义陷空山 V2 的目标架构。

V2 是一次全新重写，目标是用基于 Taro、React、TypeScript 和微信云开发的可维护架构，替换当前偏原型验证的小程序。

## 2. 架构定位

陷空山 V2 不是对现有代码库的补丁式改造。

旧项目只保留为业务参考和应急回退方案。阶段 1 验证通过后，新的产品开发应以 V2 为目标。

## 3. 核心原则

1. 页面组件只负责渲染和用户交互。
2. 领域逻辑不得嵌入页面文件。
3. 微信 API 必须隔离在基础设施适配器之后。
4. AI 提供方协议必须隔离在 `aiGateway` 之后。
5. 必须启用 TypeScript 严格模式。
6. 安全声明必须与已实现、已验证的行为一致。
7. 架构扩展前，应先通过最小纵向切片完成验证。

## 4. 目标运行时架构

```text
页面
-> 功能模块
-> 领域用例
-> 基础设施客户端
-> 云函数
-> 提供方适配器
```

## 5. 前端分层

```text
src/
├── pages/
├── features/
├── domain/
├── infra/
└── shared/
```

## 6. 分层职责

| 分层       | 职责                                 |
| ---------- | ------------------------------------ |
| `pages`    | 路由、页面外壳、生命周期装配         |
| `features` | UI 层交互编排                        |
| `domain`   | 业务类型、用例、校验规则             |
| `infra`    | 微信 API、云函数客户端、提供方适配器 |
| `shared`   | 稳定基础类型、错误、结果类型、常量   |

## 7. 云端架构

云函数作为 BFF 端点。

初始云函数：

| 函数        | 职责                               |
| ----------- | ---------------------------------- |
| `login`     | 匿名身份初始化                     |
| `aiGateway` | AI 提供方隔离和响应归一化          |
| `database`  | 后续阶段如有需要，作为数据访问边界 |

## 8. AI 网关边界

UI 绝不能消费来自 DeepSeek、OpenAI、Anthropic 或任何其他模型提供方的原生字段。

前端只消费稳定的应用层类型。

示例：

```ts
type ChatReply = {
  id: string;
  content: string;
  riskLevel: "none" | "low" | "medium" | "high";
  createdAt: number;
};
```

## 9. 阶段 1 范围

阶段 1 只验证一个纵向切片：

```text
小程序启动
-> 用户触发测试消息
-> 前端调用 aiGatewayClient
-> aiGateway 云函数返回归一化回复
-> UI 渲染回复
```

## 10. 阶段 1 非目标

> 口径澄清（见 `adr/ADR-004-mvp-scope-alignment.md`）：阶段 1 是架构验证切片，不是产品 MVP。生产视觉与风险分级是产品 MVP（阶段 2）要求。会话历史口径见 `adr/ADR-005-session-retention.md`：不做自动历史 feed，opt-in 本地留存为阶段 2 之后增量。

- 不实现完整聊天历史。
- 不实现流式响应。
- 不实现树洞。
- 不实现设置页。
- 不实现生产级危机干预流程。
- 不实现多提供方路由。
- 不声明端到端加密。
- 不迁移所有旧页面。

## 11. 后续演进

阶段 1 通过后，项目可以引入：

- `packages/domain`
- `packages/infra`
- `packages/shared`
- TanStack Query
- Zustand
- Taro 版 Tailwind
- Turbo
- CI 验证
- 生产可观测性

这些都不是阶段 1 要求。
