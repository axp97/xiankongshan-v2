# ADR-005：会话留存策略（opt-in 本地留存）

## 状态

已接受。收敛自产品专家组 × 架构专家组联合评审（2 轮）。修订 `product-definition.md §7/§9` 的"不做完整聊天历史"口径。

## 背景

初版产品契约（§9）与阶段 1 规格都写"不做完整聊天历史"，理由是匿名即逝的信任基线（§8）与反依赖设计（§7，禁用留人暗黑模式）。

但产品负责人提出：有意义的对话是用户的情感资产，**至少在用户主动要求留存时应当尊重**；若不属于 MVP，可以先只做"记录"能力。

评审的关键辨析：必须把两件事彻底分开——

- **系统驱动的留人**（streak、推送召回、"明天见"钩子、未读红点、首屏塞历史 feed）= 暗黑模式，与 §7 冲突，禁止。
- **用户驱动的留存**（默认关闭、显式发起的"我想留下这段"）= 用户能动性与尊严，**不是**暗黑模式，与产品气质自洽。

反对的从来是前者，双方对后者无冲突。

## 决策

支持 **opt-in 本地会话留存**，默认即逝，不做自动历史 feed，不做召回钩子。边界如下：

产品边界：

1. **默认即逝**：默认不留，行为与现状一致（TTL 过期、清除即硬删）。
2. **opt-in 主动留**：仅用户显式动作（"留下这段话"）才留存。
3. **访问是刻意行为**：留存入口低调，不在首页/会话首屏塞"你的历史"；不做红点、角标、未读、streak、推送召回。
4. **措辞去"记录"化**：命名为"我留下的话 / 留存"，不叫"聊天记录 / 历史"，框定为"你主动珍藏的"，非"系统给你记的账"。
5. **危机豁免**：`riskLevel = high` 命中期间隐藏"留下这段"入口（与反依赖静默同源），避免二次刺激与敏感内容落盘。
6. **可删**：留存项支持单条删除与一键清空，均为硬删。

架构边界：

1. **存储放客户端本地**（Taro Storage），不上服务端，天然守住匿名性，与现有反依赖数据同一 localStorage 边界。代价：换机/卸载丢失——与"即逝"气质自洽，需在留存 UI 明示"仅存这台设备"。
2. **服务端跨端留存显式推迟**到后续阶段，需专门隐私评审（加密、TTL、不可反查派生 key），不进当前范围。
3. **数据结构极简**：只存必要字段（本地 id、content、reply、riskLevel、createdAt），不建用户画像。
4. **领域建模**：留存是 `domain` 用例（saveTurn / listSaved / deleteSaved），不散在页面，遵循 `architecture.md §5` 分层。

## 范围归属

- **不属于阶段 1**（架构验证切片，见 ADR-004）。
- 归入**产品 MVP 之后的增量**：这次先只落"记录能力"（本地持久化 + 主动留 + 本地增删），完整浏览/检索体验后续再打磨。对应产品负责人"如果不是 MVP 可以先只做记录"。

## 影响

正向影响：

1. 尊重用户对自己内容的所有权，同时不破坏匿名即逝信任与反依赖设计。
2. 本地存储方案零新增后端面，隐私风险最低。

负向影响：

1. 本地留存换机即丢，需 UI 明确预期。
2. `product-definition.md §7/§9` 需从"不做完整聊天历史"细化措辞。

## 验证

1. `product-definition.md §9` 改为"不做系统驱动的历史 feed 与召回钩子；允许 opt-in 本地留存（见 ADR-005）"。
2. `product-definition.md §7` 注明 opt-in 主动留存不属于被禁的留人暗黑模式。
3. 留存能力实现时：默认关闭、high 期间入口静默、可硬删、仅本地存储、无服务端画像。
