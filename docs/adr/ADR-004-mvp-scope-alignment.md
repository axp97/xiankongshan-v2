# ADR-004：阶段与 MVP 口径对齐

## 状态

已接受。收敛自产品专家组 × 架构专家组联合评审（2 轮）。

## 背景

仓库内存在两份互相错位的"最小标准"，且都被口头称作 "MVP"，导致设计评审出现自相矛盾的结论：

1. `reference/陷空山UX设计/product-definition.md`（锁定版产品契约）：要求风险四档（§6）、反依赖四层（§7）、生产级体验与信任边界。
2. `docs/specs/phase-1-minimal-chat.md` + `docs/architecture.md` §9/§10 + `docs/verification.md`：把"阶段 1"定义为最小架构纵切，明确**不做生产级视觉、不做危机干预流程、不做持久化历史**。

设计（`陷空山UX设计`）以产品契约为目标，因此对照阶段 1 规格会被误判为"超范围"。根因不是设计做错，而是"阶段 1"与"产品 MVP"共用了 "MVP" 一词，混淆了两个不同层级。

裁决依据：`harness/rules.md §1`（原 `rule.md`）已规定文档冲突顺序为 `harness/rules.md` > `architecture.md` > `verification.md` > 当前生效规格 > 实现。因此"阶段 1 规格"层级低于 `architecture.md`，本 ADR 在其之上做口径澄清。

## 决策

术语分层，消除 "MVP" 一词的二义：

1. **阶段 1 = 架构验证切片（Architecture Validation Slice），明确不是产品 MVP。** 它只验证 `UI → 基础设施客户端 → aiGateway → 归一化 ChatReply → 渲染` 这条纵切跑通。不做生产视觉、不做风险分级、不做历史。
2. **产品 MVP = `product-definition.md` 契约，落在阶段 2「真实聊天主路径」。** 风险四档、反依赖四层、生产级体验、信任边界都是**产品 MVP 要求**，而不是阶段 1 要求。
3. `陷空山UX设计` 是**产品 MVP（阶段 2）的设计依据**，不是阶段 1 的验收物；其 design token 可被阶段 1 提前复用，但不作为阶段 1 验收项。

逐条消解并存矛盾：

| 冲突点 | 阶段 1（架构切片） | 产品 MVP（阶段 2 / 契约） |
|---|---|---|
| 生产级视觉 | 不做（可复用 token，不作验收项） | 做 |
| 风险 / 危机分级 | 不做 | 必做（契约 §6） |
| 反依赖四层 | 不做 | 必做（契约 §7） |
| 聊天历史 | 不做 | 不做自动历史 feed；opt-in 本地留存见 ADR-005 |
| 树洞 | 不做 | 不做（设计中仅预告文案，阶段 2 前决定去留） |

## 影响

正向影响：

1. 消除文档并存矛盾，评审不再自相矛盾。
2. 阶段 1 保持极薄，验收标准（`verification.md §3.12` "不意外实现阶段 1 非目标"）仍可判定。
3. 设计资产归位到阶段 2，可直接驱动产品 MVP 实现。

负向影响：

1. 需要同步更新 `docs/index.md`、`phase-1-minimal-chat.md`、`architecture.md` 的措辞。
2. "MVP" 一词今后必须显式限定为"产品 MVP（阶段 2）"，团队需统一话术。

## 验证

1. `docs/index.md` 阶段表标注阶段 1 = 架构验证切片（非 MVP）、阶段 2 = 产品 MVP。
2. `phase-1-minimal-chat.md` 顶部有"本规格是架构验证切片，不是产品 MVP"澄清。
3. `architecture.md` §9/§10 指向本 ADR 说明"完整聊天历史"口径。
4. 后续任何"MVP"表述都能唯一对应到阶段 2 产品契约。
